# Automated deployment

The `CI` workflow runs lint, tests (including PostgreSQL), and a Docker build on pushes and pull requests. On a push to `main`, if `DOCKERHUB_IMAGE` is configured and CI succeeds, it builds and publishes a Docker Hub image for amd64 and arm64, tagged with the full commit SHA. If deployment is also explicitly enabled, a dedicated self-hosted runner updates the existing Stratego deployment, waits for Kubernetes readiness, and attempts to restore the previous image if the rollout fails. A commit tag identifies the source revision, but a Docker Hub tag can still be overwritten unless registry policy prevents it.

Pull requests do not publish or deploy. Deployment also checks that the commit is still the head of `main` immediately before the rollout, and the deploy job uses a concurrency group. A simultaneous manual cluster update can still race with this process; avoid concurrent manual changes during deployment.

## Setup after the registry and target cluster are available

1. Prepare the cluster independently using `k8s/postgres.yaml` and `k8s/base/app.yaml` or the replicated database alternative. Create the appropriate database secret, ensure the application is ready, and configure access to the image registry on the cluster nodes. For a private Docker Hub image, configure Kubernetes `imagePullSecrets`; the GitHub runner's Docker login does not authenticate the cluster nodes.
2. In the private GitHub repository, create the repository variable `DOCKERHUB_IMAGE` as a lowercase Docker Hub `namespace/repository` and repository secrets `DOCKER_USERNAME` and `DOCKER_PASSWORD` (use a registry access token). Publishing starts on the next successful push to `main`.
3. Install a dedicated self-hosted GitHub Actions runner with the custom label `stratego-deploy`. Its OS account needs `kubectl`, network access to the target cluster, and a kubeconfig that contains the intended context. The runner must remain online to accept deployment jobs. Follow [GitHub's self-hosted runner guidance](https://docs.github.com/en/actions/reference/security/secure-use#hardening-for-self-hosted-runners): anyone able to change trusted workflow code can run commands with that runner's privileges.
4. Set repository variable `STRATEGO_KUBE_CONTEXT` to that context name and, if needed, `STRATEGO_KUBE_NAMESPACE` (defaults to `default`). Set `STRATEGO_DEPLOY_ENABLED` to `true` only once the runner and target are ready. The workflow targets the existing `stratego` deployment and container, and references the GitHub environment `stratego-deployment`; configure any desired protections for that environment.
5. Push a reviewed change to `main` and inspect the **test**, **publish**, and **deploy** jobs in Actions. A skipped publish or deploy job means deployment did not occur. Check the deployment's image, rollout status, and application health in the target cluster.

Do not commit kubeconfigs, registry credentials or Kubernetes Secrets. This workflow updates the deployment image; it does **not** apply changes to Kubernetes manifests, provision a cluster, install the database, or migrate its data. A self-hosted runner is configured for the Sydney demo described in [AWS demo](aws-demo.md); this is not a production deployment.

## Local rollout verification

`scripts/deploy.sh` accepts `KUBE_CONTEXT`, `DEPLOY_IMAGE` (a full-SHA-tagged image), and optional `KUBE_NAMESPACE`, `KUBE_DEPLOYMENT`, `KUBE_CONTAINER`, and `ROLLOUT_TIMEOUT` environment variables. It refuses an untagged image, verifies the current target, and restores the previous image on a failed rollout if the target image has not been changed by another actor. A rollback failure requires manual intervention.

On 31 October 2026, the script was tested in a disposable namespace on the local kind cluster. It rolled out a new image to two replicas and confirmed readiness; an intentionally nonexistent image timed out, returned failure, and restored the previous working image. A repeat with the already-deployed image passed, and a non-SHA tag was rejected. The same workflow and deployment script also passed an end-to-end test from a private test repository on 31 October 2026: GitHub Actions ran the tests, published an amd64/arm64 image to a private Docker Hub test repository, and a one-job self-hosted runner deployed that exact commit-tagged image to two healthy pods in an isolated local namespace. See the [successful test run](https://github.com/priyansh3105/stratego-cicd-test-1793431900/actions/runs/41181386325). The project repository publishes to the public `sharmanityam/stratego-mp2` Docker Hub repository after successful CI.
